## T1. 마이그레이션, notification 패키지

| 파일 | 변경 |
|---|---|
| `resources/db/migration/V4__create_notification.sql` (신규) | 설계 4장 SQL 그대로: `notification`(id, employee_id, type, message, created_at), `fk_notification_employee` → `users(id)`, `idx_notification_employee_created (employee_id, created_at)`. 머리 주석 한 줄(FR-09, D-42). MySQL 8.4·H2 양쪽 실행. **V1~V3는 손대지 않는다** |
| `notification/domain/NotificationType.java` (신규) | enum `ENROLLMENT_CONFIRMED`, `WAITLIST_PROMOTED` (각 Javadoc) |
| `notification/domain/Notification.java` (신규) | `@Entity @Table(name = "notification", indexes = @Index(name = "idx_notification_employee_created", columnList = "employee_id, created_at"))`. 필드: `id`(IDENTITY), `@ManyToOne(fetch = LAZY, optional = false) @JoinColumn(name = "employee_id") User employee`, `@Enumerated(STRING) @JdbcTypeCode(VARCHAR) @Column(length = 30) type`, `@Column(length = 255) message`, `Instant createdAt` — 모두 `nullable = false`. `protected` 기본 생성자, `public static Notification create(User employee, NotificationType type, String message, Instant createdAt)`, getter만 (Enrollment 엔티티와 같은 모양) |
| `notification/repository/NotificationRepository.java` (신규) | `JpaRepository<Notification, Long>`, `long countByEmployeeIdAndType(Long employeeId, NotificationType type)` (테스트·후속 조회용) |
| `notification/service/NotificationService.java` (신규) | `@Service`, 생성자 주입 `NotificationRepository`, `Clock`. `@Transactional(propagation = Propagation.MANDATORY) public void record(User employee, CourseSession session, NotificationType type)`: ① 메시지 생성(아래) ② `createdAt = clock.instant().truncatedTo(MICROS)` ③ `save(Notification.create(...))` ④ `log.info("notification type={} employeeId={} sessionId={}", type, employee.getId(), session.getId())`. 클래스 Javadoc: 같은 트랜잭션 저장(B안)과 이유, 로그에 개인정보 금지(NFR-03) |

메시지 (설계 3장):
- `ENROLLMENT_CONFIRMED`: `"'%s' %d회차 수강 신청이 확정되었습니다."` (과정 제목, 회차 번호)
- `WAITLIST_PROMOTED`: `"'%s' %d회차 대기 중이던 신청이 확정되었습니다."`
- 과정 제목은 `session.getCourse().getTitle()` (최대 100자 → 255자 이내)

**테스트**
- `NotificationServiceTest` (신규, Mockito, `Clock.fixed`): 두 type의 메시지 문구 정확히 일치, `createdAt` = 고정 시각(마이크로초), `save` 1회, 저장된 `employee`·`type`
- `SchemaMappingTest`: 코드 변경 없음. V4와 엔티티 불일치면 여기서 실패한다

## T2. EnrollmentService 연결

| 파일 | 변경 |
|---|---|
| `enrollment/service/EnrollmentService.java` | 생성자 마지막 인자로 `NotificationService notificationService` 추가. `enroll`: `saveAndFlush` 성공 **뒤**, `saved.getStatus() == CONFIRMED`면 `notificationService.record(employee, session, ENROLLMENT_CONFIRMED)` (대기 순번 계산과 순서 무관). `cancel`: `next.get().promote()` 바로 뒤 `notificationService.record(next.get().getEmployee(), session, WAITLIST_PROMOTED)`. 기존 주석의 스냅숏 전제(회차 잠금이 첫 쿼리) 유지 — `record`는 잠금 뒤에만 호출 |
| `enrollment/service/EnrollmentServiceTest.java` | `@Mock NotificationService notificationService` 추가, **`new EnrollmentService(...)` 두 곳(65줄 `setUp`, 232줄 시작 시각 테스트) 모두** 인자 추가 |

**테스트 (`EnrollmentServiceTest`)** — 설계 7장
- S1 신청 `CONFIRMED` → `record(employee, session, ENROLLMENT_CONFIRMED)` 1회
- S2 신청 `WAITING` → `verifyNoInteractions(notificationService)`
- S3 취소 후 재신청으로 `CONFIRMED` → 1회
- S4 확정자 취소 + 대기 있음 → 승급자에게 `WAITLIST_PROMOTED` 1회, 취소자로는 호출 없음 (`ArgumentCaptor<User>`)
- S5 확정자 취소 + 대기 없음, 대기자 취소 → 호출 없음
- S6 거절 경로(E001 중복, E002 종료, E003 시작 후, C002 회차 없음) → 호출 없음

`EnrollmentControllerTest`는 `@Transactional` 롤백이라 변경 없이 통과해야 한다 (알림도 함께 롤백)

## T3. 통합 테스트, 동시성 테스트 정리

**신규 `notification/NotificationIntegrationTest.java`**: `@SpringBootTest`, **클래스에 `@Transactional` 없음**(실제 커밋·롤백을 확인). 주입: `EnrollmentService`, `CourseAdminService`, `UserRepository`, `NotificationRepository`, `TransactionTemplate`(또는 `PlatformTransactionManager`로 생성), `JdbcTemplate`. 임직원은 `User.create("notify-N@test.local", "x", …, EMPLOYEE)`, 과정·회차는 `CourseAdminService`(2099년). `@AfterEach`에서 만든 행을 **알림 → 신청 → 회차 → 과정 → 사용자** 순으로 지운다(FK 순서).

| # | 준비 | 실행 | 기대 |
|---|---|---|---|
| N1 | 정원 2 회차, 임직원 1명 | `enroll` (자동 커밋) | 알림 1건, type `ENROLLMENT_CONFIRMED`, 메시지에 과정 제목·회차 번호 |
| N2 | 같음 | `transactionTemplate.executeWithoutResult(s -> { enrollmentService.enroll(...); s.setRollbackOnly(); })` | 신청 0건, 알림 0건, 회차 `confirmed_count` 0 |
| N3 | 정원 1, 임직원 2명 | 순서대로 신청 (2번째는 WAITING) | 2번째 임직원 알림 0건 |
| N4 | N3 상태 | 1번째 임직원 `cancel` | 2번째 임직원 `WAITLIST_PROMOTED` 1건, 1번째는 `ENROLLMENT_CONFIRMED` 1건만 |

**`enrollment/EnrollmentConcurrencyTest.java` `tearDown`**: `DELETE FROM users WHERE email LIKE 'load-%@test.local'` **앞에** `DELETE FROM notification WHERE employee_id IN (SELECT id FROM users WHERE email LIKE 'load-%@test.local')` 추가. 빠지면 확정 알림의 FK 때문에 사용자 삭제가 실패한다. 다른 시나리오 코드는 바꾸지 않는다. implementer는 `compileTestJava`까지, **실행은 개발자**(Docker)
